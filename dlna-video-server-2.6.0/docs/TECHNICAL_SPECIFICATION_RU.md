# DLNA VIDEO SERVER 2.0 — техническая спецификация
**Версия:** 1.1 (проектная редакция)  
**Дата:** 23 ноября 2026 г.  
**Статус:** утверждённая основа; изменения фиксируются отдельными решениями.

## 1. Назначение
Самостоятельный локальный видеосервер для обнаружения и воспроизведения видео на Smart TV и других DLNA/UPnP-клиентах. Linux — первая платформа, Windows — следующая.

## 2. Продуктовые ограничения
- Только видеофайлы и видеокаталоги.
- Без музыки, фотографий, облака, учётных записей, удалённого доступа, веб-интерфейса и интернет-каталога.
- Без MiniDLNA в качестве движка.
- Оригинальные файлы не изменяются.
- Не менять системный firewall без отдельного согласия пользователя.
- Интерфейс: Rust + Slint 1.19.
- Единое платформенно-независимое ядро Rust.

## 3. Режимы воспроизведения
### 3.1 Direct Play
Режим по умолчанию. Сервер передаёт оригинальный файл по HTTP; декодирование выполняет телевизор. Сервер не перекодирует и не изменяет файл.

### 3.2 Direct Stream / remux
Дополнительная возможность будущей реализации: смена контейнера без перекодирования медиапотоков, только если формат и протокол позволяют это безопасно. Не входит в первый рабочий срез.

### 3.3 Transcoding
Опциональная подсистема. По умолчанию выключена и не является обязательной зависимостью ядра. Может быть включена пользователем в настройках. Оригиналы остаются неизменными. Внешний движок (например, FFmpeg) не включается автоматически: его использование, лицензирование, упаковка и обнаружение должны быть отдельно утверждены и проверены.

### 3.4 Режим выбора
Пользователь выбирает:
- Только Direct Play.
- Автоматический выбор.
- Транскодирование (если движок установлен и доступен).

Автоматический режим опирается на подтверждённые возможности клиента и явно помечает неизвестные. Нельзя обещать точное определение всех поддерживаемых кодеков по одному User-Agent или UPnP-описанию.

## 4. Определение возможностей клиента
Модуль `client-compatibility`:
- идентифицирует клиента по доступным UPnP-описанию, User-Agent, HTTP-заголовкам и сетевому адресу;
- хранит модель/производителя и источник сведений;
- различает подтверждённые, предполагаемые и неизвестные возможности;
- не делает вывод «поддерживается» только по производителю;
- позволяет пользователю вручную выбрать профиль/режим для конкретного клиента;
- не блокирует Direct Play, если сведения о клиенте неполные.

## 5. Функциональные подсистемы
- `core`: общие модели, состояния и события.
- `app`: жизненный цикл и координация приложения.
- `media-library`: добавление папок, рекурсивное сканирование, индекс, обновление и удаление записей.
- `dlna`: SSDP, UPnP device description, SOAP, ContentDirectory, DIDL-Lite, ConnectionManager.
- `streaming`: HTTP GET/HEAD, Range, 206 Partial Content, MIME, несколько клиентов, безопасная выдача файлов.
- `network`: интерфейсы, IP, сетевые изменения.
- `config`: сохранение пользовательских настроек.
- `diagnostics`: журналирование и понятные сообщения об ошибках.
- `platform`: Linux- и Windows-адаптеры.
- `ui`: Slint GUI.
- `client-compatibility`: сведения о клиентах и оценка совместимости.
- `transcoding`: необязательный адаптер транскодирования.

## 6. Видеотека
- Пользователь добавляет и удаляет корневые папки.
- Сканирование рекурсивное.
- Индекс хранит метаданные, но не копирует видео.
- Обрабатываются кириллица, пробелы, длинные пути, недоступные и удалённые файлы.
- База данных — SQLite после отдельного выбора и проверки схемы миграций.

## 7. Сеть и протоколы
Реализовать SSDP discovery/advertisements, UPnP device/service descriptions, SOAP actions, ContentDirectory, DIDL-Lite, ConnectionManager и HTTP streaming. Стабильный UUID устройства. Корректное завершение и восстановление после изменения сети.

## 8. Безопасность
- HTTP-ресурс может ссылаться только на файл внутри разрешённой видеопапки.
- Защита от path traversal и обхода символьными ссылками за пределы разрешённых корней.
- Не открывать доступ к произвольным локальным файлам.
- Не менять firewall автоматически.
- Сетевой сервер предназначен для локальной сети.

## 9. Платформы
### Linux first
Пакетирование, автозапуск, трей, Anti-Sleep через платформенный адаптер. Интеграция с KDE/другими окружениями по возможности, без зависимости ядра от конкретного рабочего стола.

### Windows next
Отдельный платформенный адаптер для автозапуска, системного трея и предотвращения сна. Протокольное ядро и библиотека общие.

## 10. Критерии приёмки
Проект не считается готовым по одному `cargo check`. Нужны:
- unit- и integration-тесты;
- тесты SSDP/UPnP/SOAP/DIDL-Lite;
- тесты HTTP Range и перемотки;
- тесты нескольких одновременных клиентов;
- тесты сетевых отключений и перезапусков;
- воспроизведение на реальных телевизорах целевых поколений;
- отдельная проверка Direct Play и каждого включённого режима транскодирования.
